## 1. 测试目标

### 1.1 总体目标

对 Practice Software Testing — Toolshop 电商工具商店系统的 Sprint 5 with bugs 版本进行**系统级手工功能测试**，发现并记录 UI 展示、功能逻辑、数据交互层面的缺陷，评估系统当前版本的质量状况，为后续修复和版本迭代提供决策依据。

### 1.2 具体目标

| 序号 | 目标描述 | 量化指标 |
| --- | --- | --- |
| 1 | 覆盖系统核心功能模块的功能测试 | 登录、注册、首页、商品详情、购物车、结账 7 大模块覆盖率 ≥ 90% |
| 2 | 设计并执行符合行业规范的测试用例 | 测试用例总数 ≥ 60 条 |
| 3 | 发现并记录功能缺陷 | 提交结构化 Bug 报告 ≥ 20 个 |
| 4 | 评估版本质量状态 | 输出完整的测试报告，明确给出上线建议 |
| 5 | 实践黑盒测试设计方法 | 等价类划分、边界值分析、场景法至少各应用 5 次以上 |
| 6 | 建立可复用的测试资产 | 测试用例可复用于后续版本回归测试 |

### 1.3 测试关注点

- **功能正确性**：核心业务功能是否按需求正确实现
- **UI 一致性**：页面展示是否与设计规范一致（布局、文案、图标、配色）
- **数据交互**：前端操作是否触发了正确的后端请求，请求参数是否完整
- **边界与异常处理**：系统对非法输入、空数据、边界条件的容错与提示是否合理
- **跨浏览器兼容性**：Chrome、Edge、Firefox 三大主流浏览器下的展示与交互一致性

## 6. 测试策略

### 6.1 整体策略

本次测试采用**基于风险的手工功能测试策略**，以用户使用频率最高、业务价值最大的核心功能为测试重点。测试分为两个层级：

- **Level 1 — 单模块功能测试**：独立验证每个模块的显示和操作功能
- **Level 2 — 端到端业务流程测试**：串联多个模块，验证完整用户场景

### 6.2 测试设计方法

| 方法 | 应用说明 |
| --- | --- |
| **等价类划分** | 将输入数据划分为有效等价类和无效等价类，每类选取代表性数据进行测试。应用于登录（邮箱/密码）、注册（12个字段各自的合法/非法值）、搜索等 |
| **边界值分析** | 针对输入输出范围的边界条件进行测试。应用于密码长度（9/10/40/41）、价格区间（1/200）、商品数量（10/11）、年龄边界（18岁）等 |
| **场景法** | 从用户视角模拟真实业务流程，端到端串联多个功能。应用于游客购物流程、已登录用户下单流程 |
| **错误推测法** | 基于经验推测可能存在的错误。应用于特殊字符输入、字段绑定错误、参数缺失等场景 |
| **UI 对比验证** | 对比页面实际渲染效果与设计规范的差异。应用于文案拼写、图标完整性、字体一致性等 |

### 6.3 测试优先级

| 优先级 | 定义 | 覆盖内容 |
| --- | --- | --- |
| **P0（极高）** | 核心业务功能，影响系统基本可用性 | 登录鉴权、注册、Home 导航、商品浏览、加购、购物车结算、支付、端到端购物流程 |
| **P1（高）** | 重要功能，影响用户体验 | 多条件组合筛选、表单校验细节、边界值、异常场景、跨浏览器关键差异 |
| **P2（中/低）** | 辅助验证，非核心功能 | UI 样式细节、文案拼写、字体一致性、图标完整性 |

### 6.4 Bug 严重性与优先级定义

#### 严重性

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| **致命** | 系统崩溃、数据丢失、核心业务流程完全阻塞 | 支付网关不可用、价格筛选完全失效 |
| **严重** | 核心功能无法使用，无替代方案 | 导航跳转404、数量调整失效、排序全反 |
| **较严重** | 核心功能可勉强使用但存在明显缺陷 | 密码校验失效、登录信息展示异常 |
| **一般** | 功能可用但存在问题，有替代操作 | 字段绑定错误、Tab顺序错乱 |
| **轻微** | 不影响功能的UI瑕疵 | 文案拼写错误、字体不一致、图标破损 |

#### 优先级

| 级别 | 定义 |
| --- | --- |
| **极高** | 必须在当前版本修复，阻塞上线 |
| **高** | 应在当前版本修复，严重影响用户体验 |
| **中** | 宜在下个版本修复，对用户体验有可感知影响 |
| **低/次要** | 可在后续迭代中择机修复 |

### 6.5 Bug 生命周期管理

```
新建(New) → 已确认(Confirmed) → 已指派(Assigned) → 进行中(In Progress) → 已修复(Resolved) → 已验证(Verified) → 已关闭(Closed)
```

### 6.6 回归测试策略

- 每个 Bug 修复后，执行该 Bug 对应的原始测试用例进行验证
- 对修复模块的关联功能执行冒烟级别的快速回归
- 在版本迭代前，全量回归执行 P0 级别测试用例

## 7. 风险控制

### 7.1 风险识别与应对

| 序号 | 风险描述 | 影响程度 | 发生概率 | 应对措施 |
| --- | --- | --- | --- | --- |
| R1 | 被测环境不稳定或服务宕机 | 高 | 低 | 1. 确认系统托管在公网，一般稳定性良好；2. 如遇服务不可用，切换至本地抓包或 API 文档验证模式 |
| R2 | 测试时间不足，无法覆盖全部计划范围 | 中 | 中 | 1. 严格按优先级执行，P0 用例优先保障；2. P2 用例可缩减；3. 每日汇报进度，动态调整计划 |
| R3 | 对业务逻辑理解偏差导致用例设计方向错误 | 中 | 低 | 1. 参考官方 Bug 清单和 Swagger 文档验证理解；2. 与 AI 导师（TestMentor）确认不确定的测试场景 |
| R4 | 浏览器兼容性问题导致跨浏览器测试耗时超出预期 | 低 | 中 | 1. 以 Chrome 为主测试浏览器，Edge 和 Firefox 仅做关键差异对比；2. 非关键兼容性问题记录但不阻塞进度 |
| R5 | Bug 数量远超预期，缺陷记录耗时过多 | 低 | 高 | 1. 使用统一的 Bug 报告模板提高记录效率；2. 优先记录 P0/P1 级别 Bug；3. 类似的 UI 类缺陷可合并记录 |
| R6 | 部分功能模块测试数据准备复杂 | 低 | 低 | 1. 利用系统内置测试账号和预置数据；2. 注册新账号作为测试数据准备手段 |

### 7.2 风险监控机制

- 每日回顾当日测试进度与发现的 Bug 数量，判断是否偏离计划
- 如某模块 Bug 密度异常偏高（如 100% 用例失败），暂停新用例设计，优先深入测试该模块
- 测试周期过半时进行中期评审，评估是否能按时完成所有 P0 用例
